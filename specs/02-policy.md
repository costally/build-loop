의사코드의 allow는 해당 검사만의 통과를 의미한다. 최종 작업 실행은 적용되는 모든 검사의 통과가 필요하다. wait/block은 문서·코드·승인 상태를 임의 변경하지 않는다.

## 1. 회원/인증 정책

계정·회원 가입 기능은 현재 확정 요구에 없다. Codex 인증은 호스트가 담당하며 build-loop가 인증 정보 복사를 요구하지 않는다. 본 절은 프로젝트 승인 권한을 정의한다.

### POL-001 단계 승인과 완료 승인 구분

- **규칙**: 사용자의 명시적 응답을 해당 승인 대상·버전에 연결하며 브리프·PRD·스펙 세트·최종 결과물의 승인을 서로 대신하지 않는다.
- **구현 판정**: 승인에는 대상·버전·사용자 응답·호스트 출처 검증을 연결한다. 임의 user 표기만으로 승인하지 않는다. 호스트 출처가 미실증이면 미확인으로 두고 승인 전환을 통과시키지 않는다.
- **적용 시점**: 문서 승인 기록, 구현 착수 전환, 시연 이후 완료 전환.
- **위반/실패 시 처리**: 전환을 차단하고 기록한다. 문구: "이 단계의 사용자 승인이 없습니다. 승인 대상과 버전을 확인해 주세요." 대상·버전이 없거나 모호하면 "승인 대상을 확인해 주세요."
- **예외**: 이미 동일 대상·동일 버전의 유효 승인이 있으면 다시 묻지 않는다. 사용자의 문맥상 명시 승인도 허용하되 단순 감탄·응답 없음·기본 선택을 승인으로 간주하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol001(request, approvals) {
    if (!request.target || !request.version) return block("승인 대상을 확인해 주세요.");
    const valid = approvals.some(a => a.source === "user" && a.verifiedHostEvent && a.explicit
      && a.target === request.target && a.version === request.version && !a.revoked);
    return valid ? allow() : wait("이 단계의 사용자 승인이 없습니다. 승인 대상과 버전을 확인해 주세요.");
  }
  ```
- **관련 요구사항**: REQ-005, REQ-008
- **관련 화면**: SCR-004, SCR-007
- **관련 테스트**: TC-005, TC-008, TC-010, TC-022, TC-025, TC-029, TC-042 — PRD 승인만으로 구현·최종 완료 전환하는 위반 사례 포함.

## 2. 콘텐츠/데이터 정책

### POL-002 설치·프로젝트 경계

- **규칙**: 기본 루트 C:/build-loop의 system/은 도구, projects/<이름>/docs/·code/는 사용자 프로젝트로 구분하고 기존 파일 충돌 및 다른 프로젝트 쓰기는 차단한다.
- **운영 적용**: 도구 자체의 1차 설치·실행 대상은 Windows 터미널의 Codex CLI와 현재 GPT PC 앱의 Codex 작업 환경다. macOS·Linux의 지원을 통과로 표시하지 않는다. 관리 프로젝트의 결과물 유형은 별도 인터뷰로 정한다.
- **구현 판정**: 각 프로젝트는 독립 Git 루트, .build-loop/state.sqlite와 .build-loop/evidence/는 로컬 실행 자료이며 DB·원본 로그는 기본 Git 제외다.
- **적용 시점**: 설치·재설치·프로젝트 생성·선택·파일 쓰기·도구 배포 준비.
- **위반/실패 시 처리**: 쓰기를 차단하고 원본을 보존한다. 문구: "기존 파일 또는 프로젝트 경계와 충돌합니다. 대상 경로를 확인해 주세요: {경로}" 도구 배포에 프로젝트가 포함되면 "사용자 프로젝트가 도구 배포에 포함되어 배포 준비를 중단했습니다."
- **예외**: 명시적으로 선택된 프로젝트 내부 수정과 관리 대상 도구 파일의 검증된 업데이트는 허용한다. 최초 설치 루트 생성은 허용하되 기존 파일의 자동 덮어쓰기는 허용하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol002(op) {
    const target = resolveRealTargetWithExistingParent(op.path);
    if (op.overwritesUnmanagedFile || !insideAllowedRoot(target, op.context))
      return block(`기존 파일 또는 프로젝트 경계와 충돌합니다. 대상 경로를 확인해 주세요: ${target}`);
    if (op.kind === "tool-package" && op.containsUserProject)
      return block("사용자 프로젝트가 도구 배포에 포함되어 배포 준비를 중단했습니다.");
    return allow();
  }
  ```
- **관련 요구사항**: REQ-001, REQ-002
- **관련 화면**: SCR-001, SCR-002
- **관련 테스트**: TC-001, TC-002, TC-011, TC-019, TC-020, TC-030, TC-031 — 중복 이름·경로 이탈·기존 파일 덮어쓰기·배포 혼입 포함. 경계 검사는 접두사 문자열 비교가 아닌 실제 경로 단위로 검사.

### POL-003 선택 UI·답변 확정·복구

- **규칙**: 한 질문에 실제 선택 UI로 2~3개 대안·추천·이유를 제시하고 유효한 사용자 답만 확정하며 UI 장애는 답변을 보존해 동일 질문부터 복구한다.
- **운영 적용**: 인터뷰는 결과물 유형·실행/시연 환경·배포 필요 여부·핵심 확인 흐름을 한 결정씩 확인한다. 실제 선택 UI·추천·이유·동일 질문 복구 원칙은 유지한다.
- **적용 시점**: 각 인터뷰 질문 표시·답변 수신·재개·선택 도구 오류.
- **위반/실패 시 처리**: 질문 진행을 멈추고 미응답 질문을 보존한다. 문구: "선택 메뉴를 사용할 수 없습니다. 답변을 보존하고 복구 후 같은 질문에서 이어갑니다." 빈 답에는 "선택하거나 의견을 입력해 주세요. 아직 답변은 확정되지 않았습니다."
- **예외**: 메뉴의 자유 의견 입력은 유효한 답으로 처리한다. 사용자가 이전 결정을 명시적으로 변경하면 변경관리로 연결한다. 취소·닫기·빈 답은 추천안 선택으로 취급하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol003(question, event, capability) {
    if (!capability.realSelectionUi) {
      preservePending(question);
      return wait("선택 메뉴를 사용할 수 없습니다. 답변을 보존하고 복구 후 같은 질문에서 이어갑니다.");
    }
    if (!validOptions(question, 2, 3) || !hasRecommendationWithReason(question))
      return block("질문에 선택지와 추천 이유를 먼저 작성해야 합니다.");
    if (!event) return show(question);
    if (!event.fromUser || event.cancelled || !event.answer.trim())
      return wait("선택하거나 의견을 입력해 주세요. 아직 답변은 확정되지 않았습니다.");
    return saveConfirmedAnswer(question.id, event.answer);
  }
  ```
- **관련 요구사항**: REQ-003
- **관련 화면**: SCR-001, SCR-003, SCR-006
- **관련 테스트**: TC-001, TC-003, TC-012, TC-019, TC-021, TC-024, TC-026, TC-027, TC-032 — 연속 질문·중단 후 복구·빈 답·취소·텍스트 전용 자동 전환 위반 포함.

### POL-004 상태 저장·재개 일관성

- **규칙**: 확정 답·단계·작업·증거·미응답 질문·승인 대기를 저장하고 재개 시 실제 문서·코드 버전과 대조해 불일치·손상·동시 쓰기를 감지한다.
- **구현 판정**: SQLite 트랜잭션으로 현재 상태·사건 이력을 함께 저장한다. expected_revision 충돌은 거절하고 쓰기 잠금 대기는 최대 5초다. 커밋 전·중·후 종료를 시험하고 재개 시 DB 무결성·승인 manifest·코드/증거 버전을 확인한다. 손상은 원본 보존·차단이며 미커밋 변경을 새 승인·통과로 만들지 않는다.
- **적용 시점**: 결정 확정·상태 전환·중단·재개·상태 파일 쓰기.
- **위반/실패 시 처리**: 원본을 보존하고 자동 전환을 차단한다. 문구: "저장 상태와 실제 파일이 다릅니다. 확인이 필요한 항목을 표시했습니다." 동시 쓰기에는 "다른 세션이 이 프로젝트를 갱신했습니다. 최신 상태를 불러온 뒤 다시 진행합니다."
- **예외**: 상태와 실제 자료가 일치하면 확정 답을 재질문하지 않는다. 승인·검증이 없는 자료를 발견해도 승인·통과 기록을 추정해 복구하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol004(state, files, expectedRevision) {
    if (state.revision !== expectedRevision)
      return block("다른 세션이 이 프로젝트를 갱신했습니다. 최신 상태를 불러온 뒤 다시 진행합니다.");
    if (!validState(state) || !matchesRecordedVersions(state, files))
      return wait("저장 상태와 실제 파일이 다릅니다. 확인이 필요한 항목을 표시했습니다.");
    return resumeFirstIncomplete(state);
  }
  ```
- **관련 요구사항**: REQ-004
- **관련 화면**: SCR-002, SCR-003, SCR-005, SCR-006
- **관련 테스트**: TC-002, TC-003, TC-004, TC-007, TC-013, TC-020, TC-021, TC-023, TC-024, TC-027, TC-031, TC-037, TC-038, TC-041 — 세 단계 재개·파일 외부 변경·손상·앱/CLI 동시 수정 포함. 트랜잭션·revision·최대 5초 잠금 대기를 적용.

## 3. 결제/과금 정책

해당 없음 — 도구 자체의 결제·요금 기능은 확정 요구에 없다. Codex 구독·사용량 또는 관리 프로젝트의 배포 비용이 무료라고 가정하지 않는다. 비용 정책·예산 한도는 미정이며 별도 승인 없이 유료 서비스를 신청하지 않는다.

## 4. 알림 정책

별도 이메일·메신저·푸시 알림은 해당 없음. 현재 Codex 대화에 상태·질문·실패 원인을 표시한다. 외부 알림 채널이 필요하면 신규 요구로 검토한다.

## 5. 권한/등급 정책

회원 등급 대신 프로젝트 작업 역할을 구분한다.

| 역할 | 설명 | 주요 권한 |
|---|---|---|
| 사용자 | 프로젝트 의도와 결과물 판단 주체 | 스펙·주요 변경·최종 완료 승인, 중단 |
| Codex | 승인 범위의 작성·구현 수행 | 문서 초안, 구현·검증·복구, 승인 요청. 자기 승인 불가 |
| 제어 장치 | 저장 상태·조건 검사 | 허용 작업 판정·기록·복구 안내. 사용자 의사 추정 불가 |

외부 사용자 계정·협업 권한·역할별 로그인은 미정이며 본 표가 계정 기능을 추가하지 않는다.

## 6. 운영/어뷰징 정책

### POL-005 단계·스펙 이탈 검사

- **규칙**: 필수 산출물·승인·검증이 충족된 경우만 다음 단계로 전환하고 승인 스펙 안의 실패는 복구하되 범위·주요 설계·완료 기준 변경은 사용자에게 판단받는다.
- **운영 적용**: 실행·배포 준비 중 계정·인증·권한·비용 결정 또는 사용자 직접 조치가 필요하면 정확한 대상·범위·필요 조치를 표시하고 대기한다. 사용자 응답·권한을 추정하지 않는다. 기존 의사코드의 pendingUserDecision 또는 externalBlock 조건을 적용한다.
- **산출물 검사**: 실제 화면은 SCR/HTML 쌍·구성요소·기본/로딩/빈/에러를 검사한다. 비화면 부분은 04-interactions의 REQ별 입력 예시·기대 출력·실행 순서·기본/실행중/입력없음/실패·유효성/오류 원문·POL/TC를 검사한다. 혼합 제품은 각 부분을 IA와 승인 manifest에 연결하며 비화면용 제품 화면을 강제 생성하지 않는다.
- **구현 판정**: 주요 변경은 요구/제외 범위·인수 기준·승인 데이터 구조·외부 서비스/계정·개인자료 전달·운영 데이터의 파괴적 변경을 뜻한다. 모호한 경우 기존 스펙과 차이를 제시해 사용자가 판단한다.
- **적용 시점**: 도구 실행 전·단계 전환·작업 종료·변경 리뷰.
- **위반/실패 시 처리**: 전환을 차단하고 허용되는 다음 작업을 표시한다. 문구: "현재 단계의 완료 조건이 충족되지 않았습니다. 다음 작업: {작업}" 범위 변경에는 "확정 스펙을 바꾸는 결정이 필요합니다. 변경안을 확인해 주세요."
- **예외**: 사용자 답변 대기·명시적 중단·환경 차단은 미완료 개발로 간주해 강제 계속하지 않는다. 내용상 이탈은 인수 조건·차이 리뷰로 확인하며 경로 검사만으로 통과하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol005(context) {
    if (context.userStopped || context.pendingUserDecision || context.externalBlock)
      return wait(context.reason);
    if (context.requiresScopeOrMajorDesignOrAcceptanceChange)
      return wait("확정 스펙을 바꾸는 결정이 필요합니다. 변경안을 확인해 주세요.");
    if (!context.requiredArtifactsReady /* 화면/비화면의 필수 요소별 검사 */ || !context.validApproval || !context.validEvidence)
      return block(`현재 단계의 완료 조건이 충족되지 않았습니다. 다음 작업: ${context.nextAllowedTask}`);
    return allow();
  }
  ```
- **관련 요구사항**: REQ-005, REQ-006
- **관련 화면**: SCR-004, SCR-005, SCR-006
- **관련 테스트**: TC-005, TC-006, TC-014, TC-022, TC-023, TC-024, TC-028, TC-032, TC-033, TC-034, TC-035, TC-036, TC-042 — 단계별 필수 조건을 대입해 검사. 미승인 구현·순서 이탈·답변 대기 중 자동 진행 포함.

### POL-006 동일 오류 최대 3회 복구

- **규칙**: 최초 실패 후 동일한 미해결 오류에 대한 자동 수정·재검증은 최대 3회 수행하고 각 시도의 원인·수정·검증 결과를 기록한다.
- **구현 판정**: 오류 키는 project_id+task_id+check_id+failure_category+environment_id다. 문구·세션·단순 코드 변경으로 초기화하지 않는다. 복구 실행 직전 시도를 저장하고 수정·재검증을 1회로 센다. 시작 후 종료로 결과가 없으면 미확인으로 남겨 횟수를 유지한다. 실제 해당 검증 통과로 해결하거나 변경 조건·사용자 재시도 근거로 새 주기를 기록하고 과거 이력을 보존한다.
- **적용 시점**: 선택 UI 복구·구현 검증 실패·단계 검사 실패 후 자동 복구를 시작하기 직전과 결과 수신 시.
- **위반/실패 시 처리**: 3회 모두 실패하면 복구 시도를 멈추고 현재 상태·시도 이력·필요 조치를 보존한다. 문구: "같은 오류의 자동 복구를 3회 시도했지만 해결되지 않았습니다. 진행 상태를 보존했습니다. 필요한 조치: {조치}"
- **예외**: 최초 실패 검증은 3회에 포함하지 않는다. 사용자 중단·질문 대기·인증·권한 부족 같은 외부 차단은 즉시 대기하며 횟수를 소진하지 않는다. 재시작·문구 변화만으로 횟수를 초기화하지 않는다. 새 조건에서 다시 시도하려면 변경 근거 또는 사용자 재시도 결정을 기록한다.
- **검증 의사코드**:
  ```js
  function checkPol006(issue, context) {
    if (context.userStopped || context.pendingUserDecision || context.externalBlock)
      return wait(context.reason);
    if (issue.failedRecoveryAttempts >= 3)
      return wait(`같은 오류의 자동 복구를 3회 시도했지만 해결되지 않았습니다. 진행 상태를 보존했습니다. 필요한 조치: ${issue.requiredAction}`);
    return allowOneRecordedRecovery(issue.id);
  }
  ```
- **관련 요구사항**: REQ-003, REQ-006, REQ-007
- **관련 화면**: SCR-003, SCR-005, SCR-006
- **관련 테스트**: TC-006, TC-015, TC-021, TC-023, TC-024, TC-027, TC-028, TC-033, TC-039, TC-040 — 최초 실패+3회 실패 후 4번째 자동 복구 차단, 세션 재개 후 횟수 보존, 대기 상태 즉시 중지 포함. 동일 오류 키·미확인 시도·주기 기준은 위 구현 판정에 따름.

### POL-007 검증 결과와 버전 연결

- **규칙**: 검증 결과는 대상 코드·스펙·환경 버전에 연결해 통과·실패·미실행·차단으로 기록하고 현재 결과물에 유효한 필수 검증 및 시연이 갖춰진 뒤 사용자 완료 승인을 요청한다.
- **운영 적용**: 필수 검증은 프로젝트 인터뷰에서 합의한 실행·배포·시연 대상 환경을 기준으로 한다. 준비하지 못한 외부 환경은 차단·미확인으로 기록하고 임의로 로컬 환경으로 축소하지 않는다. evidenceAppliesTo는 합의 환경의 일치도 확인한다.
- **구현 판정**: 검증 근거는 대상 스펙 manifest·코드·환경에 연결한다. 다른 검사·환경의 통과가 오류 해결이나 현재 결과물의 증거를 대신하지 않는다.
- **적용 시점**: 검증 실행·코드 변경·시연 준비·완료 전환.
- **위반/실패 시 처리**: 완료 요청 준비를 차단한다. 문구: "현재 결과물에 유효한 검증 또는 시연 확인이 부족합니다. 미확인 항목: {목록}"
- **예외**: 조건에 해당하지 않는 시험은 사유를 기록하되 사용자와 합의한 완료 기준을 임의 축소하지 않는다. 로컬 시험은 외부 운영 환경 시험을 대신하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol007(deliverable, checks) {
    const missing = requiredChecks(deliverable).filter(id =>
      !checks.some(c => c.id === id && c.result === "passed"
        && evidenceAppliesTo(c, deliverable)));
    if (missing.length || !deliverable.demoEvidence)
      return block(`현재 결과물에 유효한 검증 또는 시연 확인이 부족합니다. 미확인 항목: ${missing.join(", ") || "시연"}`);
    return readyForUserApproval();
  }
  ```
- **관련 요구사항**: REQ-007, REQ-008
- **관련 화면**: SCR-005, SCR-007
- **관련 테스트**: TC-007, TC-008, TC-016, TC-023, TC-025, TC-029, TC-032, TC-033, TC-040, TC-042 — 오래된 통과 결과·미실행·차단을 통과로 처리하는 위반, 사용자 승인 전 완료 전환 포함.

### POL-008 승인 이후 변경·고도화

- **규칙**: 승인 스펙 변경은 CR로 영향과 사용자 판단을 기록한 뒤 반영하고 완료 후 추가 기능은 이전 완료 버전을 보존한 다음 작업으로 관리한다.
- **적용 시점**: 승인 문서 수정·사용자 피드백 분류·완료 이후 개선 요청.
- **위반/실패 시 처리**: 승인 문서 직접 수정을 차단한다. 문구: "승인된 스펙의 변경입니다. 변경요청과 사용자 승인을 먼저 확인해 주세요."
- **예외**: 승인 전 초안 수정은 직접 가능하다. 승인 스펙에 맞추는 코드 버그 수정은 새 범위를 만들지 않으며, 버그·요구 변경 구분이 모호하면 차이를 제시해 사용자가 판단한다.
- **검증 의사코드**:
  ```js
  function checkPol008(change) {
    if (change.touchesApprovedSpec && !change.validApprovedCR)
      return block("승인된 스펙의 변경입니다. 변경요청과 사용자 승인을 먼저 확인해 주세요.");
    if (change.ambiguousBugOrNewScope) return wait("기존 스펙과 변경안 중 어느 쪽이 맞는지 확인해 주세요.");
    if (change.afterCompletion) preservePreviousCompletion(change.previousVersion);
    return allow();
  }
  ```
- **관련 요구사항**: REQ-009
- **관련 화면**: SCR-004, SCR-007
- **관련 테스트**: TC-009, TC-017, TC-022, TC-025 — 승인 문서 직접 수정·과거 완료 기록 덮어쓰기·모호한 피드백 임의 분류 포함.

## 7. 법적/개인정보 정책

### POL-009 배포·기록의 자료 분리

- **규칙**: 결정·진행·승인·검증 기록은 완료 후에도 로컬 프로젝트에 보관하고 build-loop의 별도 서버·GitHub 자동 전송 및 자동 삭제를 하지 않으며, 도구 배포·공개 기록·검증 로그에 비밀 값을 포함하지 않는다.
- **적용 시점**: 기록 저장·프로젝트 완료·전송·삭제·도구 패키징·Git 스테이징·공개 배포 준비.
- **위반/실패 시 처리**: 기록 또는 배포를 중단하고 비밀 값 대신 항목 종류·경로만 보고한다. 문구: "공개하면 안 되는 자료가 포함되어 기록 또는 배포를 중단했습니다. 제외 항목을 확인해 주세요." 기록 자동 전송·삭제에는 "진행 기록의 자동 전송 또는 자동 삭제는 허용되지 않습니다."
- **예외**: 사용자가 실제 제품 배포를 승인한 프로젝트 코드는 해당 프로젝트 배포에 포함할 수 있다. 비밀 값 노출 허용으로 해석하지 않는다.
- **검증 의사코드**:
  ```js
  function checkPol009(operation) {
    if (operation.automaticRecordTransfer || operation.automaticRecordDeletion)
      return block("진행 기록의 자동 전송 또는 자동 삭제는 허용되지 않습니다.");
    if (operation.containsSecrets || (operation.isToolDistribution && operation.containsUserProject))
      return block("공개하면 안 되는 자료가 포함되어 기록 또는 배포를 중단했습니다. 제외 항목을 확인해 주세요.");
    return allow();
  }
  ```
- **관련 요구사항**: REQ-001, REQ-002, REQ-004
- **관련 화면**: SCR-001, SCR-002, SCR-007
- **관련 테스트**: TC-001, TC-018, TC-019, TC-020, TC-025, TC-031 — 토큰·환경 파일·프로젝트 자료 혼입과 로그 비밀 출력 포함.

사용자가 선택한 보관 방향은 로컬 프로젝트에 계속 보관하는 것이다. 별도 보관 만료나 자동 삭제를 두지 않는다. build-loop의 별도 서버·GitHub 자동 전송은 하지 않는다. 이는 Codex 서비스 자체의 데이터 처리 방식을 변경하거나 로컬 전용 모델 실행을 보장하는 설정이 아니다. 저장 항목별 민감정보 제외·사용자 요청 시 삭제 절차는 후속 설계·검토에서 구체화한다.
