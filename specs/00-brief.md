## 1. 한 줄 정의

> 아이디어를 가진 사용자가 인터뷰로 스펙을 확정하고, Codex 전용 하네스의 안내·검사를 통해 최종 개발 결과물까지 완성하도록 돕는 GitHub 배포용 도구.

## 2. 해결하려는 문제

- 구체화되지 않은 아이디어를 개발 가능한 문서와 확정 스펙으로 만들어야 한다.
- 개발 중 Codex가 의도와 다른 방향으로 진행할 수 있어, 도구가 스펙 확정부터 개발 완료까지 계속 진행을 이끌어야 한다.
- 사용자가 확인한 문제는 두 가지다: 합의한 스펙과 다른 구현, 중단·재개 시 결정·진행 맥락 유실. 두 문제 모두 해결 대상이다.
- 사용자 사례: C:/dev, C:/codex-flow, C:/lumen에서 여러 방식을 시도했으나, GitHub에 둔 프로세스에서 Codex가 조금씩 벗어나 사용자가 바로잡아야 결과물 방향으로 돌아오는 경험을 함. 구체적인 단일 이탈 동작·발생 원인은 아직 확인하지 않음.

## 4. 핵심 가치 제안

- 인터뷰·스펙 확정과 개발 하네스를 하나의 연속 과정으로 연결한다.
- Codex가 확정 스펙을 따라 최종 결과물까지 진행하도록 이끈다. 지침과 실행 검사 각각의 책임·지원 범위는 미정 — 확인 필요.
- 사용자가 반복해서 프로세스 복귀를 지시하는 부담을 줄인다. 확정 스펙 안의 누락·순서 이탈·검증 실패는 자동 복구하고, 범위·주요 설계·완료 기준 변경은 사용자 판단을 받는다.

## 5. 핵심 기능 (3~5개, 우선순위순)

1. 인터뷰로 아이디어를 구체화하고 기획 문서와 스펙을 확정한다. 한 번에 한 질문, 실제 선택 UI에 구체적인 대안과 추천 표시·이유를 제공한다. 인터뷰 도중 이 방식이 사라져 텍스트 입력만 요구되는 문제를 해결 대상으로 포함한다.
2. 확정 스펙을 개발 작업과 연결한다.
3. 하네스 엔지니어링으로 개발 과정의 이탈을 방지·탐지한다.
4. 개발·검증·수정과 실제 시연을 연결하고, 사용자의 명시적 1차 완료 승인까지 진행한다. 승인 후 추가 기능·고도화는 다음 작업으로 관리한다.
5. GitHub 배포본을 C:/build-loop에 설치하고 여러 프로젝트를 관리한다. 도구는 system/, 프로젝트별 실제 스펙은 projects/<이름>/docs/, 구현 코드는 projects/<이름>/code/에 둔다. GitHub 배포 대상은 도구이며 사용자 프로젝트를 섞지 않는다.

위 목록은 요청 흐름이며, 출시 우선순위는 미정 — 확인 필요.

## 6. 성공 기준

- 사용자 의도: 아이디어 입력부터 스펙 확정, 개발 완료, 최종 결과물까지 도구의 안내가 이어진다.
- 각 관리 프로젝트의 완료 기준은 초기 인터뷰에서 용도에 맞게 확정한다. 웹서비스의 배포·실사용, 로컬 도구의 설치·실행 등 최종 확인 환경과 핵심 흐름을 합의하며, 합의된 기준을 충족해야 완료로 본다.
- 완료 판정은 합의한 1차 범위의 구현·검증 후 실제 시연·사용을 거쳐 사용자가 명시적으로 승인할 때 성립한다. 자동 테스트 통과나 Codex의 완료 선언만으로 완료 처리하지 않는다. 사용자가 문제를 발견하면 수정·재검증·재시연으로 돌아간다. 승인 이후 추가 기능·고도화는 다음 작업으로 관리한다.
- 측정할 실제 시나리오·완료 증거·이탈 판단 기준·기간: 미정 — 확인 필요.
- 확인된 검증 방향: 연속 인터뷰와 중단 후 재개에서도 선택 UI·추천 표시·이유를 유지하고, 스펙 내부 이탈은 사용자 복귀 지시 없이 복구한다. 지원할 Codex 환경과 검사 횟수·증거는 미정 — 확인 필요. 실제 선택 도구 제공 여부를 먼저 확인하며 텍스트 목록을 실제 메뉴라고 부르지 않는다.

## 8. 범위에서 제외하는 것

- Claude 등 Codex 이외 에이전트 지원.
- 그 밖의 1차 출시 제외 범위: 미정 — 확인 필요.
- 관리할 결과물 유형은 Windows 프로그램·웹페이지·플러그인 등을 프로젝트별 인터뷰에서 정한다. 도구 자체의 지원 OS와 각 결과물 유형의 자동 배포 지원 범위는 별도로 확정해야 한다.
- 기존 C:/dev·C:/codex-flow·C:/lumen은 사례 조사 대상이며, 이번 요청으로 기존 파일 이동·통합·삭제를 결정한 것은 아님.
