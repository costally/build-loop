## 1. 개요

### 1.1 배경

기존 시도에서 사용자가 Codex의 프로세스 이탈을 반복해서 바로잡았다. build-loop는 인터뷰·확정 스펙·현재 단계·검증·사용자 완료 승인을 연결한다. 실제 선택 메뉴가 사라지는 문제와 중단·재개 시 결정 유실을 핵심 실패 조건으로 취급한다. 기존 시도의 정확한 실패 원인은 미확인이다.

### 1.2 목표

아래 정량 검증 목표는 제안이며 후속 QA 단계에서 사용자 확인이 필요하다.

| # | 목표 | 성공 지표 | 목표치 |
|---|---|---|---|
| 1 | 선택형 인터뷰 유지 | 앱·CLI 각각 연속 질문의 선택지·추천·이유·답변 저장 | 각 10문항 중 누락 0건, 제안 |
| 2 | 재개 시 결정 유지 | 인터뷰·개발·완료 확인 대기 중 종료 후 복구 | 세 시점 모두 확정 답 재질문 0건, 제안 |
| 3 | 과정 이탈 복구 | 미승인 구현·순서 건너뛰기·검증 실패 후 완료 시도 | 세 시나리오 모두 차단 또는 미완료 판정 후 다음 허용 작업 제시, 제안 |
| 4 | 사용자가 결과물 확인 | 합의된 핵심 흐름 시연 후 명시적 완료 승인 기록 | 승인 없는 완료 상태 0건 |

### 1.3 범위 제외 (Out of Scope)

- Codex 외 에이전트 지원.
- 이번 기획만으로 기존 C:/dev·C:/codex-flow·C:/lumen을 이동·삭제하지 않는다.
- 1차는 신규 프로젝트의 전체 흐름을 완성한다. 기존 프로젝트 폴더 연결·자동 이관은 후속 기능으로 둔다(사용자 선택).
- 도구 자체의 1차 환경은 Windows 터미널의 Codex CLI와 현재 GPT PC 앱의 Codex 작업 환경 모두다. macOS·Linux는 후속이며 관리 프로젝트의 결과물 유형은 Windows 프로그램으로 제한하지 않는다.
- 실행·시연·배포 환경은 프로젝트별 인터뷰에서 합의하고 필요한 준비·검증을 수행한다. 모든 플랫폼 전용 어댑터 제공을 전제로 하지 않으며 미지원·불가 조건은 표시한다.

## 2. 사용자

### 2.1 페르소나

| 페르소나 | 설명 | 핵심 니즈 |
|---|---|---|
| 아이디어를 개발하려는 사용자 | 요청자 포함. 개발 경험별 세분화는 미정 | 선택형 인터뷰, 스펙 확인, 개입 없이 과정 유지, 실제 결과물 승인 |

### 2.2 사용자 스토리

- 아이디어를 가진 사용자로서 구체적인 대안과 추천 이유를 선택하며 개발 스펙을 확정하고 싶다.
- 개발을 맡긴 사용자로서 중단 후에도 같은 결정과 작업 상태로 이어가고 싶다.
- 결과물을 사용하는 사람으로서 실제 작동을 확인한 뒤 1차 완료를 승인하고 싶다.

### REQ-001 설치·환경 확인

- **설명**: GitHub 배포본을 기본 C:/build-loop에 설치한다. 도구 본체와 사용자 프로젝트를 분리하며 앱·CLI의 지원 가능 상태를 검사한다.
- **사용자 시나리오**: 설치 후 프로젝트를 만들고 Windows 터미널의 Codex CLI와 현재 GPT PC 앱의 Codex 작업 환경에서 시작한다. 기능 지원은 각각 실제로 검사한다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] system/과 projects/를 구분하고 기존 사용자 파일이 있으면 덮어쓰기 없이 충돌 경로를 보고한다.
  - [ ] 앱·CLI별 버전·선택 질문·훅 확인 결과를 지원/미지원/미확인으로 기록한다. 단순 설정 활성화를 실제 동작 통과로 표시하지 않는다.
  - [ ] 기존 PowerShell codex 함수와 전역 설정을 무단 대체하지 않으며 재설치 후 프로젝트 문서·코드·결정을 유지한다.
- **예외/에러 케이스**: 미지원 버전·신뢰되지 않은 훅은 정상 설치 완료와 구분한다. 정확한 복구 문구·지원 버전은 후속 정책에서 정의한다.

### REQ-002 프로젝트 관리

- **설명**: projects/<프로젝트명>/docs/와 code/를 실제 작업 경로로 사용한다. 기획 문서는 docs/ 안에 브리프·PRD·정책·IA·화면·TC·변경 이력을 구성한다.
- **사용자 시나리오**: 여러 프로젝트 중 하나를 선택해 해당 문서와 코드를 이어서 작업한다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 프로젝트 생성·목록·선택 시 실제 절대 경로를 표시하고 선택한 프로젝트 밖의 다른 프로젝트 파일은 수정하지 않는다.
  - [ ] 도구 배포 Git의 변경 목록에 사용자 프로젝트 파일이 포함되지 않는다. 각 프로젝트 폴더를 독립 Git 루트로 두고 docs/·code/를 관리한다. 실행 DB는 .build-loop/state.sqlite, 로컬 증거는 .build-loop/evidence/이며 DB·원본 로그는 기본 Git 제외다.
- **예외/에러 케이스**: 중복 이름·경로 충돌은 기존 프로젝트 선택 또는 새 이름 입력으로 처리하며 기존 프로젝트를 초기화하지 않는다.

### REQ-003 선택형 인터뷰

- **설명**: 질문마다 실제 선택 UI에 2~3개 구체 대안·추천 표시·추천 이유·업무상 차이를 제시한다. 한 번에 한 결정을 확인하며 자유 의견도 수용한다.
- 인터뷰 결정 항목: 결과물 유형·실행/시연 환경·배포 필요 여부·핵심 확인 흐름. 한 번에 한 결정을 묻는다.
- **사용자 시나리오**: 사용자가 대안을 고르면 담당 문서와 결정 기록에 반영하고 다음 질문을 구체화한다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 매 질문에 추천 선택지와 근거가 있고 확정 답을 다시 묻지 않는다. 빈 답·닫기·취소를 확정 선택으로 저장하지 않는다.
  - [ ] 선택 UI를 사용할 수 없으면 질문·기존 답을 보존하고 버전·모드·설정을 확인한다. 가능한 복구 후 동일한 미응답 질문을 실제 선택 UI로 재개한다.
  - [ ] 텍스트 목록을 실제 메뉴라고 부르거나 장애 시 텍스트 전용 인터뷰로 자동 전환하지 않는다. 재시작·사용자 조치가 필요하면 필요한 조치와 재개 위치를 표시한다.
- **예외/에러 케이스**: 복구 불가능한 환경은 차단 상태와 원인을 기록한다. 추천 선택지를 사용자 응답 없이 자동 확정하지 않는다.

### REQ-004 상태 저장·재개

- **설명**: 확정 답·근거 문서·단계·작업·검증 증거·미응답 질문·승인 대기를 대화 밖에 저장하고 재개 시 실제 파일과 대조한다.
- 두 작업 환경은 같은 프로젝트 문서·코드·진행 기록을 재개 근거로 사용한다. 동일 대화 세션 자체의 동기화를 보장하는 요구는 아니다.
- **사용자 시나리오**: 앱·CLI를 종료하거나 새 대화로 바꾼 뒤 같은 프로젝트를 이어간다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 인터뷰·개발·완료 승인 대기 각각에서 재개하면 마지막 확정 결정과 첫 미완료 작업을 복구한다.
  - [ ] 상태와 실제 파일·코드 버전이 다르면 차이를 보고하고 사용자 승인·시험 통과를 추정해서 채우지 않는다.
  - [ ] 상태 파일이 손상되면 기존 파일을 보존하고 복구 가능한 마지막 상태 및 미확인 항목을 표시한다.
- **예외/에러 케이스**: 앱·CLI 동시 쓰기 충돌은 조용한 덮어쓰기 없이 감지한다. SQLite 트랜잭션으로 상태·사건을 함께 커밋하고 expected_revision을 비교한다. 쓰기 잠금 대기는 최대 5초이며 낡은 revision은 거절한다. 비정상 종료 후 무결성·manifest·코드/증거 버전을 대조하고 손상·불일치는 원본 보존·차단한다.

### REQ-005 스펙 확정

- **설명**: 브리프→PRD→정책→IA·화면→QA TC를 연결하고 사용자 확인 및 최종 스펙 승인을 받는다. 결과물 유형과 완료 환경을 프로젝트 인터뷰에서 정한다.
- **사용자 시나리오**: 사용자가 문서·목업을 확인한 뒤 구현할 스펙을 승인한다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] P0 요구에 인수 조건·정책·화면·TC 연결이 있고 미정 항목 및 해당 없음의 근거를 확인할 수 있다. 사용자 화면은 SCR/HTML 쌍, 화면 없는 부분은 docs/04-interactions/REQ-###-<동작명>.md로 입력 예시·기대 출력·실행 순서·4종 상태·유효성/오류 문구·POL/TC를 정의한다. 혼합 제품은 둘 다 작성하고 IA·승인 manifest로 연결한다.
  - [ ] 스펙 승인 대상 문서의 버전과 사용자 응답을 연결하며 문서 존재·검토중 상태·브리프 방향 확인만으로 구현 착수 승인을 만들지 않는다.
- **예외/에러 케이스**: 필수 미정·깨진 참조가 남으면 해당 단계에서 보완한다. 승인 문서 변경은 REQ-009에 따른다.

### REQ-006 단계·작업 제어

- **설명**: 단계별 허용 작업과 전환 조건을 검사한다. 스펙 안의 누락·순서 이탈·검증 실패는 자동 복구하고 범위·주요 설계·완료 기준 변경은 사용자에게 묻는다.
- 사용자 판단 대상은 요구/제외 범위·인수 기준·승인 데이터 구조·외부 서비스/계정·개인자료 전달·운영 데이터의 파괴적 변경이다. 승인 범위 안의 버그 수정은 자동 복구하고 모호하면 차이를 제시한다.
- **사용자 시나리오**: Codex가 승인 전 구현하거나 검증을 건너뛰려 할 때 검사 결과에 따라 허용 작업으로 돌아간다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 미승인 구현·단계 건너뛰기·증거 없는 완료 시도를 구분해 차단 또는 미완료 판정하고 복귀 작업을 기록한다.
  - [ ] 의미상 스펙 이탈은 변경 내용·인수 조건·리뷰로 확인하며 파일 경로 검사만으로 스펙 준수를 통과시키지 않는다.
  - [ ] 사용자 답변 대기·명시적 중단 시 자동 계속 진행하지 않는다. 반복 실패 한도 도달 시 상태·실패 원인·필요 조치를 남긴다. 한도는 POL-006의 동일 오류 최대 3회다. 오류 키·미확인 시도·주기 보존 기준은 POL-006에 따른다.
- **예외/에러 케이스**: 훅 미제공·비활성·출력 오류를 감지한 경우 강제 검사 적용 상태를 통과로 표시하지 않는다.

### REQ-007 구현·검증 반복

- **설명**: 작업을 승인 요구사항에 연결하고 코드 변경, 해당 검증, 실패 수정, 재검증을 수행한다.
- 전달 준비: 프로젝트별 필요한 설정·설치·실행 또는 배포 절차를 구성하고 수행 가능한 작업과 검증을 진행한다. 계정·인증·권한·비용 결정이나 직접 조치가 필요하면 대상·범위·필요 조치만 요청하고 대기한다.
- **사용자 시나리오**: 검증 실패 시 승인 범위 안에서 수정하고 검증을 다시 실행한다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 각 구현 작업에 관련 요구 ID와 변경 파일·실행 검증·결과·대상 코드 버전을 기록한다.
  - [ ] 통과·실패·미실행·차단을 구분하며 외부 서비스·운영 환경을 검증하지 못하면 로컬 시험만으로 통과 처리하지 않는다.
  - [ ] 대상 코드가 변경되면 영향을 받는 이전 검증을 재평가하고 필요한 검증을 재실행한다.
- **예외/에러 케이스**: 외부 권한·인증·비용·사용량 문제는 차단 원인과 사용자 조치를 기록한다. 범위를 임의 축소해 통과시키지 않는다.

### REQ-008 시연·완료 승인

- **설명**: 합의된 1차 범위의 실제 사용 환경에서 핵심 흐름을 시연·사용하고 사용자 명시 승인으로 완료한다.
- 합의한 실행·시연·배포 환경에서 증거를 확인한다. 외부 환경을 준비하지 못하면 차단·미확인으로 표시하고 시연 목표를 임의로 로컬 환경으로 축소하지 않는다.
- **사용자 시나리오**: 사용자가 결과물을 써 보고 1차 완료를 확인하거나 문제를 알려준다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 구현·검증 후 시연 대상 버전·실행 방법·핵심 흐름·확인 결과를 제시하고 사용자 확인 대기로 전환한다.
  - [ ] 사용자 명시 승인 전에는 완료 상태로 바꾸지 않는다. 승인 기록은 대상 결과물 버전과 연결한다.
  - [ ] 사용자 문제 제기가 합의 범위의 실패이면 수정·재검증·재시연하고 새 범위 요청이면 REQ-009로 연결한다.
- **예외/에러 케이스**: 사용자가 응답하지 않거나 시연 환경이 준비되지 않으면 대기·차단 상태를 유지한다. 승인으로 해석할 문맥·무효화 조건은 정책에서 정의한다.

### REQ-009 추가 기능·고도화

- **설명**: 승인된 스펙 변경과 완료 이후 추가 기능을 기존 승인 이력을 보존하며 다음 작업으로 관리한다.
- **사용자 시나리오**: 완료한 프로젝트에 기능을 추가하거나 사용 후 개선을 요청한다.
- **인수 조건 (Acceptance Criteria)**:
  - [ ] 승인된 요구 변경은 변경 사유·영향 ID·변경안·사용자 판단을 기록한 후 문서·목업·TC와 구현을 갱신한다.
  - [ ] 완료 이후 추가 요청은 이전 완료 버전·승인을 보존하고 새 범위·인수 조건·검증·완료 승인을 연결한다.
- **예외/에러 케이스**: 버그 수정인지 새 요구인지 불명확하면 기존 스펙과 비교한 차이를 보여주고 사용자가 판단한다.
